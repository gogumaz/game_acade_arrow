## 0. 프로세스 원칙

모든 작업 유닛(WU)은 하네스의 4단계 사이클을 **독립적으로** 통과한다.

| 단계 | 담당 | 산출물 | 게이트 |
|---|---|---|---|
| Phase 1 — Q&A 착수 | qa-interviewer / qa-intake | `00_qa_intake.md` | 이해도 90%+ · 치명적 열린 질문 0 · 사용자 승인 |
| Phase 2 — 계획 | task-planner / work-planning | `01_work_plan.md` | 사용자 승인 |
| Phase 3 — 실행 | task-executor / work-execution | 코드·문서 + `02_execution_log.md` | 계획 완료 기준 충족 |
| Phase 4 — 독립 검증 | quality-verifier | `03_quality_report.md` | PASS (FIX/REDO는 원인 단계로 회귀) |

- 각 유닛의 작업 기록은 `_workspace/<번호>_<유닛명>/`에 저장한다.
- **코드 작성은 각 유닛의 Phase 3에서만 한다.** Phase 1·2에서 코드를 만들지 않는다.
- 기획서 v4.1이 이미 확정한 사양은 Phase 1에서 재질문하지 않는다 — 유닛별 Q&A는 아래 표의 "잔여 결정 사항"만 다루므로 짧게 끝나는 것이 정상이다.
- 검증 FIX는 해당 유닛 안에서 수정하고, REDO는 원인 단계(Q&A/계획/실행)로 되돌린다.
- 유닛 범위 밖 요구사항이 발견되면 해당 유닛을 멈추지 말고 **새 Q&A 사이클로 분리**한다.

## 4. 유닛 공통 규칙

1. **워크스페이스 명명:** 1차는 `_workspace/3_impl_wu01/` ~ `3_impl_wu09/`, 2차는 `4_ops_wu10/` ~ `4_ops_wu13/`.
2. **커밋 단위:** 유닛의 Phase 4 PASS 후 커밋한다. 커밋 메시지에 유닛 번호를 붙인다 (예: `WU-02: game core engine`).
3. **회귀 방지:** 각 유닛의 Phase 4는 해당 유닛 완료 기준에 더해 **이전 유닛의 인수 테스트 항목을 스모크로 재실행**한다.
4. **[보류] 항목:** Serial I/O·물리 키·Ubuntu 통합은 §18.5 어댑터 전략대로 인터페이스만 구현하고 실제 값 교체는 외부 사양 확정 시 별도 유닛으로 연다.
5. **순서 조정:** 의존 관계를 지키는 범위에서 유닛 순서는 계획 단계에서 조정할 수 있다 (예: WU-07 연출은 WU-03 이후 아무 때나).
6. **참조 저장소:** `game_acade_puzzle`은 전 유닛에서 읽기 전용 참조 구현으로 유지한다.

## 6. 유닛별 상세 프로세스 (v2.0 신설)

각 유닛을 하네스 4단계로 전개한 상세 실행 계획이다. **Phase 2의 태스크 분해는 초안**이며, 해당 유닛의 task-planner가 이를 기점으로 계획서를 확정한다. "확정 사양(재질문 금지)"에 적힌 절은 기획서 v4.1에서 이미 확정된 것으로, 유닛 Phase 1에서 다시 질문하지 않는다. 각 유닛의 **의존 관계·완료 시 상태는 §2·§3 표를 단일 기준**으로 하며 본 절에 중복 기재하지 않는다.

### 6.0 공통 진행 절차

| 순서 | 작업 | 기록 |
|---|---|---|
| 1 | Phase 1: 잔여 질문만 Q&A → 이해도 90% 확인 → 착수 리포트 승인 | `<ws>/00_qa_intake.md` |
| 2 | Phase 2: 태스크 초안(아래 표)을 기점으로 계획 확정 → 사용자 승인 | `<ws>/01_work_plan.md` |
