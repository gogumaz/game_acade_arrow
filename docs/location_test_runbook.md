# ARROW OUT 로케이션 KPI 게이트 런북

기준: `arrow_out_arcade_gdd_v1_0.md` §1.5·§14.4  
판정 모델: `src/ops/locationGate.ts`

이 런북은 WU-09 이후 WU-10 이전의 운영 게이트다. 합성 플레이나 개발자 테스트는 실제 수익·재도전·공정성·가동률을 대신할 수 없다.

## 1. 통과 조건

| KPI | 산식 | 통과선 | 주 원천 |
|---|---|---:|---|
| 수익 | 유료 플레이 합계 / 매장·영업일 수 | 35회/일 이상 | 관리자 `TODAY PAID PLAY COUNT`, `stats.csv` |
| 재도전 | 10분 내 추가 결제 세션 / 10분 완전 관찰 세션 | 18% 이상 | `credit_log.csv` 결제 시각 + 현장 세션 표식 |
| 공정성 | 포커스 오인·판정 이의 실패 / 전체 실패 입력 | 1.5% 이하 | 실패 입력 기록 + 현장 확인 |
| 가동률 | (계획 가동 분 − 유료 불가 분) / 계획 가동 분 | 99% 이상 | 영업시간표 + 장애·SAFE PAUSE·정비 기록 |

네 지표가 모두 통과하고 입력 무결성 오류가 0건이어야 `readyForSecondPhase`가 참이다. 표본·분모가 없으면 `insufficient`이며 통과로 간주하지 않는다.

## 2. 매장·영업일 마감 기록

한 행은 한 매장·한 현지 영업일이다. 같은 `locationId + date`를 두 번 넣지 않는다.

| 필드 | 단위 | 기록 규칙 |
|---|---:|---|
| `locationId` | 문자열 | 개인 정보가 아닌 고정 매장 코드 |
| `date` | 날짜 | 매장 현지 `YYYY-MM-DD` |
| `paidPlays` | 회 | 이벤트·테스트 플레이 제외 |
| `reattemptOpportunities` | 세션 | 첫 결제 뒤 10분을 끝까지 관찰한 이용 세션만 포함 |
| `reattemptsWithin10Min` | 세션 | 위 분모 중 실제 추가 결제가 있었던 세션 |
| `failedInputs` | 회 | 막힌 사슬을 당겨 실패 판정이 발생한 입력 |
| `focusDisputes` | 회 | 현장 확인에서 포커스 대상 오인 또는 판정 이의로 분류된 실패 |
| `scheduledMinutes` | 분 | 계획된 유료 운영 시간 |
| `unavailableMinutes` | 분 | 결제·조작·저장·게임 진행 중 하나라도 불가능했던 시간 |

개인 이름·연락처·얼굴·카드·QR 식별자는 기록하지 않는다. 이용 세션은 당일 임시 순번으로만 구분하고 마감 집계 후 폐기한다.

## 3. 현장 절차

1. 영업 시작 전 빌드 버전·매장 코드·시각·저장소 상태를 기록한다.
2. 관리자 `OVERVIEW`, `INPUT TEST`, `STORAGE TEST`, 사운드·화면 테스트를 통과시킨다.
3. 유료 플레이마다 당일 임시 세션 순번을 부여하고 첫 결제 시각을 기록한다.
4. 10분 관찰이 끝난 세션만 재도전 분모에 넣고, 추가 결제가 있으면 분자에 넣는다.
5. 실패 판정이 발생하면 이용자 행동을 방해하지 않는 범위에서 포커스 오인·판정 이의 여부만 분류한다.
6. 유료 플레이가 불가능한 장애는 시작·복구 시각과 원인을 기록한다. 계획 정비도 불가 시간에 포함한다.
7. 마감 시 관리자 일 통계와 `credit_log.csv`를 대조하고 한 행으로 집계한다.
8. 집계 행을 `evaluateLocationGate()`에 전달한다. 오류가 있으면 원자료를 수정하고, 값을 추정해 채우지 않는다.

예제 `docs/location_observation.example.json`을 복사해 실제 관찰값으로 채운 뒤 저장소 루트에서 실행한다.

```powershell
node scripts/location-gate.mjs path\to\location_observations.json
```

Node.js 22 이상을 사용한다. 네 지표 PASS는 종료 코드 0, 유효하지만 FAIL·`insufficient`인 보고서는 2, JSON 구조·파일 오류는 1이다. 출력 JSON과 원본 관찰 파일을 같은 판정 기록에 보관한다.

## 4. 현재 자동화 범위와 한계

- `paidPlays`는 기존 `stats.csv`에서 직접 얻는다.
- `credit_log.csv`에는 `pay/start`, `pay/continue` 시각이 있어 결제 사건은 대조할 수 있다.
- 동일 이용자 여부는 개인정보 없이 런타임이 자동 확정할 수 없으므로 현장 임시 세션 표식이 필요하다.
- 포커스 오인·판정 이의는 실패 입력만으로 자동 분류할 수 없어 현장 확인이 필요하다.
- 계획 영업시간은 게임이 알 수 없으므로 매장 운영표가 필요하다.
- `play_log.csv`와 KPI 관리자 화면은 §14.2의 2차 범위이므로 이 게이트에서 선행 구현하지 않는다.

## 5. 판정 후 처리

- 전부 PASS: 2차 기능 우선순위 Q&A를 열고 WU-10부터 번호를 부여한다.
- 하나라도 FAIL: 해당 KPI의 원인 가설과 조정값을 기록하고 다음 관찰 구간에서 재측정한다.
- `insufficient`: 관찰을 계속한다. PASS나 FAIL로 보간하지 않는다.
- 무결성 오류: 중복 행, 음수·소수 카운트, 분자>분모, 불가 시간>계획 시간을 원자료에서 바로잡는다.
